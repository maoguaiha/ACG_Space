# 🏗️ 动漫分享博客网站 - 技术架构设计文档 (V1.0)

## 一、 架构设计目标

本系统旨在构建一个兼顾**低运营成本、高响应速度、极佳 SEO 收录**以及**高扩展性**的垂直内容社区。核心设计目标包括：

1. **动静分离与极速首屏：** 核心内容页具备强 SEO 能力，支持毫秒级首屏加载。
2. **后台敏捷开发：** 最小化管理端开发成本，高度复用现有企业级轮子。
3. **高并发柔性可用：** 在面对突发流量（如热门新番开播、爆款文章产生）时，保障主链路（浏览、评论）可用，次要链路（积分计算）异步削峰。

## 三、 逻辑系统架构

系统采用经典的前后端分离与微服务设计理念（当前阶段为**单体架构+分布式组件**），整体分为以下几层：

Plaintext



```
[ 客户端层 ]
├── 搜索引擎爬虫 (Google/Baidu) -> 抓取 CDN 上的 HTML 静态页面
└── 真实用户浏览器 (PC/Mobile) -> 访问前台 (Nuxt3) / 访问后台 (RuoYi)

[ 接入与分发层 ]
├── CDN (内容分发网络) -> 分发 JS/CSS/图片 及 SSG 预渲染的静态 HTML
└── Nginx -> 反向代理后端 API，处理 SSL 证书，提供接口层面的负载均衡预留

[ 应用服务层 (Spring Boot) ]
├── Web 交互网关 (Controller) -> 全局异常拦截、参数校验、限流拦截 (RateLimiter)
├── 权限安全组件 (Spring Security) -> JWT 签发与鉴权、VIP 接口访问控制
├── 核心业务逻辑 (Service)
│   ├── PGC 内容服务 (番剧管理、文章解析)
│   ├── 互动与积分服务 (评论树构建、积分发放逻辑)
│   └── 商业化服务 (广告位物料下发、会员状态校验)
└── 异步任务调度 (Quartz/Spring Task) -> 定时触发 Nuxt3 的 ISR 增量重新构建

[ 基础设施与中间件层 ]
├── Redis Cache -> 缓存首页推荐、番剧详情、用户 Token、防刷计数器
└── RocketMQ -> [Topic: Comment_Event] -> 异步消费积分计算与头衔晋升记录

[ 数据存储层 ]
└── MySQL -> 结构化数据存储 (采用读写分离架构预留)
```

## 四、 核心技术方案设计

### 4.1 混合渲染与 SEO 方案 (Nuxt 3 SSG + CSR)

- **构建阶段 (SSG)：**

  开发打包时，Nuxt 3 读取后台数据库中的“公开动漫列表”和“公开文章”，生成纯静态的 `.html` 文件并上传至 OSS。搜索引擎爬虫抓取时，直接获取带有完整 `meta` 标签和文字内容的 HTML，无需等待 JS 执行。

- **客户端水合 (CSR 介入)：**

  用户打开该静态 HTML 后，Vue 框架在后台“静默唤醒”。随后通过 AJAX 异步请求 `个人头像`、`当前总积分`、`动态评论区`、`广告位物料` 等高频变化数据，拼接在页面上。

- **更新机制 (Webhook 触发)：**

  当管理员在后台修改了某部番剧的介绍，RuoYi 后端将通过 Webhook 发送 HTTP 请求给前端的构建服务器，触发该单一页面的重新生成并覆盖 OSS 上的旧文件。

### 4.2 基于 RocketMQ 的异步积分引擎

为了防止大量用户同时发表评论时造成数据库事务积压，系统采用“发布-订阅”模型解耦互动与积分逻辑：

1. **用户操作：** 用户提交评论。
2. **同步响应：** Controller 校验内容合法性后，将评论写入 `biz_comment` 表，直接给前端返回 `200 OK`，用户立刻看到自己的评论。
3. **异步投递：** Controller 同时向 RocketMQ 发送一条 `Comment_Created_Message`（包含 UserID 和 CommentID）。
4. **消费与计算：** 后台的积分消费者（Consumer）订阅该消息。
   - 从 Redis 读取该用户当日已获取积分次数（防刷限流）。
   - 若未达上限，则更新 MySQL 中用户的总积分。
   - 判定是否需要升级头衔（若升级，可追加发送一条站内信消息）。
   - 记录数据至 `biz_user_points_log` 流水表。

### 4.3 Redis 缓存与数据一致性策略

- **缓存结构：**

  - `anime:detail:{id}` -> Hash 结构，存储番剧基础信息。
  - `ad:space:{position_code}` -> String 结构 (JSON)，存储广告位物料。
  - `sys:dict:{type}` -> List 结构，存储分类标签字典。

- **一致性保障：**

  采用“延迟双删”**或**“更新数据库后直接删除缓存 (Cache Aside)”策略。因为是纯 PGC 架构，修改频次极低且均由管理员操作，直接采用后者即可满足一致性要求。

## 五、 核心数据库规范与建模约束

基于 RuoYi 框架的规范，所有业务表均需遵循以下设计约束：

1. **公共字段标配：** 所有业务表必须包含 `create_by`, `create_time`, `update_by`, `update_time`, `remark` (备注)。
2. **逻辑删除控制：** 必须包含 `del_flag` (0代表存在，2代表删除) 字段，严禁物理删除数据，便于后期审计和恢复。
3. **主键策略：** 采用单机发号器或 Snowflake 算法生成全局唯一的 `bigint` 作为主键（避免使用自增 ID 暴露业务量）。
4. **索引规范：**
   - 查询高频字段（如：番剧表的 `publish_year`, 评论表的 `anime_id`）必须建立普通索引。
   - 积分流水表的 `user_id` 和 `create_time` 建立联合索引，便于快速统计当日积分。
