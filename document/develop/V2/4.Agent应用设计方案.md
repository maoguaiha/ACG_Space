# ACG Space — 用户端 AI 助手（Agent 应用）设计方案 V1.1

> 状态：设计稿（待确认后进入实现）
> 日期：2026-07-28
> 已锁定决策：
>
> - 定位：**用户端对话式 AI 助手**（落点：Nuxt 3 用户端）
> - 模型：**云端大模型 API**（OpenAI 兼容协议）
> - 实现形态：**纯 Python agent 服务嵌入项目**，Java 守门面（鉴权 + 持久化 + SSE 代理）；技术栈"加 Python"不"改 Java"
> - 能力：**RAG 问答 + 一个只读 Bangumi 查询工具（function calling）**，不执行任何写操作
> - 语料：平台规则文档 + 手写 FAQ + 本地番剧快照（当前 70 条，随平台增长自动重导出）
> - 番剧推荐：**从 Bangumi 实时拉取**（全球番剧库），与平台自有数据解耦，天然支撑未来数据扩充

## 1. 背景与目标

ACG Space 已是成熟的动漫内容与数字谷子集换社区，具备：抽赏、合成、背包、跳蚤市场、兑换、订单、番剧库（Bangumi 接入）、站内信（`BizMessage`/`ConversationVO`）等完整能力。

当前用户痛点：

1. **规则复杂**：抽赏保底、碎片合成（10N→1SR）、积分、UR 兑换、物流核销等机制，新用户难以快速理解。
2. **找番困难**：番剧库日益增长，用户想要"类似 XX 的番""这季有什么新番"时缺乏自然语言入口。

**目标**：在用户端增加一个常驻的 AI 助手（对话式），基于社区自有知识库做 RAG 问答，并具备**只读的 Bangumi 查询工具**用于番剧发现与推荐：

- 解答平台规则、玩法、活动；
- 基于番剧库做自然语言推荐与答疑（"类似 XX 的番""这季新番推荐"）；
- 引导操作（"怎么兑换实物"→ 给出步骤 + 页面入口）；
- **不**做任何写操作、不触发抽赏/合成/下单，纯咨询 + 只读外部查询，安全边界清晰。

### 为什么番剧推荐走 Bangumi（而非只靠本地快照）

- **平台自有数据（BizAnime，当前 70 条）**：代表"本平台收录/可集换的番"，是 RAG 语料的一部分，用于"平台有哪些番""某番在本站的情况"类问答；随业务增长重导出 `anime.json` 即可自动纳入。
- **Bangumi 全局库（api.bgm.tv）**：代表"全世界番剧"，用于"类似 XX 的番""这季新番""机战番推荐"等开放推荐，Agent 通过只读工具实时查询，不受平台数据规模限制。
- **二者解耦**：平台数据增长 → 重导出快照；推荐广度永远由 Bangumi 兜底。未来即便平台番剧库上万条，推荐能力也不依赖把全量番剧塞进向量库。

```

└───────────────────────────────────┬──────────────────────────────────┘
                                     │ HTTPS (SSE text/event-stream)
┌───────────────────────────────────▼──────────────────────────────────┐
│  Java 后端 (门面, com.ruoyi.project.agent)                            │
│  AgentController (/api/agent/**)                                       │
│    ├─ SecurityUtils 鉴权 → user_id（不进 permitAll）                   │
│    ├─ 持久化 AgentConversation / AgentMessage (MyBatis-Plus, MySQL)    │
│    ├─ Resilience4j 限流 + 熔断                                         │
│    └─ WebClient(SSE) 代理 → python-agent 内网服务，逐块转发 SseEmitter  │
└───────────────────────────────────┬──────────────────────────────────┘
                                     │ 内网 HTTP SSE
┌───────────────────────────────────▼──────────────────────────────────┐
│  python-agent 服务 (FastAPI, 无状态 AI 大脑, 无 DB)                    │
│    ├─ RAG retriever  (规则 + FAQ + 本地番剧快照, 内存余弦 / Chroma)     │
│    ├─ LLM client      (OpenAI 兼容, stream=True + function calling)    │
│    └─ Tools(只读):                                                   │
│         search_bangumi(keyword)      → GET /search/subject/{kw}?type=2 │
│         get_bangumi_detail(id)       → GET /v0/subjects/{id}          │
│         get_airing_now()             → GET /calendar                  │
│         (仅 GET + User-Agent, 无 API key, TTL 缓存)                   │
└───────────────────────────────────┬──────────────────────────────────┘
                                     │ HTTPS (User-Agent only)
┌───────────────────────────────────▼──────────────────────────────────┐
│  api.bgm.tv  (番剧全局库, 推荐广度来源)   +   云端大模型 (Chat+Embedding) │
└──────────────────────────────────────────────────────────────────────┘
```

**为什么这样分（对比 V1.0 的 Java 全量实现）**：

- **Python 只做 AI 大脑**：无状态、无 DB，RAG/function-calling 生态最成熟，代码量约为 Java 自研的一半。
- **Java 守门面**：登录态（`SecurityUtils`）、会话/消息持久化（MyBatis-Plus）、限流熔断（Resilience4j）、SSE 代理全部留在已有体系内，零破栈、零新中间件。
- **Bangumi 工具零额外凭据**：复用 Java 端 `bangumi.api.base-url` / `bangumi.api.user-agent` 配置项（从 `.env` 注入），番剧查询仅需 User-Agent，与 LLM 密钥无关。
- **语料与推荐解耦**：平台自有数据走 RAG（可随业务增长重导出）；推荐广度走 Bangumi 实时（无限）。

## 3. 技术选型与依赖

| 关注点       | 推荐方案                                                              | 说明                                                                                  |
| -------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| LLM 编排    | 纯 Python + OpenAI SDK（或 `httpx` 自调 `/v1/chat/completions`）            | 小语料自写 RAG 仅数百行；不强制 langchain，控制力更强                                             |
| Chat 模型  | `qwen-plus` / `glm-4-flash` / `deepseek-chat`（OpenAI 兼容）              | 推荐**同一家同时提供 chat + embedding**，避免双供应商                                                  |
| Embedding | 云端 `text-embedding-v3`(通义) / `embedding-3`(智谱)                     | 维度 768~1536；本地 `bge-small-zh`(sentence-transformers) 备选，零成本但需下载模型                       |
| 向量检索     | 内存余弦（v1）/ Chroma（升级）                                              | 语料仅数百段，线性扫描足够快；Chroma 提供持久化与 HNSW                                                |
| 工具调用     | OpenAI **function calling**（`tools` 参数）                              | LLM 自主决定何时查 Bangumi；失败时回退 RAG                                                       |
| 流式       | SSE（`text/event-stream`）+ FastAPI `StreamingResponse`                 | Python 侧 `stream=true`，按 `data:{json}` 逐块推                                                       |
| 前端流消费    | `fetch` + `ReadableStream`（Nuxt server 代理，规避 CORS）                  | 同 V1.0                                                                               |
| Python 框架 | FastAPI + uvicorn/gunicorn                                         | 异步、SSE 友好；CORS 仅放行内网                                                          |
| 缓存       | Python 内存 TTL 缓存 Bangumi 响应（如 1h）                                  | 尊重 Bangumi rate limit（匿名约 1~3 req/s）                                                 |
| 序列化      | **Fastjson2**（Java 侧既有约束，仅作用于门面持久化）                                | Python 侧用 Pydantic / JSON                                                             |
| 密钥       | 仅 `.env`（python-agent/.env）+ Railway 变量；不硬编码                          | `llm.base-url / api-key / chat-model / embed-model`、`bangumi.base-url / user-agent` |
| 容器       | `python-agent/Dockerfile` + `docker-compose.yml` 加 service               | 与 backend / front-ui 同编排                                                            |

> **关键约束**：DeepSeek **没有** embedding 接口。若选 DeepSeek 做 chat，必须搭配另一个 embedding 供应商（智谱/通义/OpenAI）或本地 BGE。**最简方案 = 通义或智谱一家打通 chat+embedding**。

```
│   ├── main.py            # FastAPI 入口, CORS 仅内网, /chat (SSE) + /health + /rebuild
│   ├── config.py          # 读 .env (llm.*, bangumi.*)

│   ├── prompts.py         # system prompt + 安全边界 + 来源署名
│   └── schemas.py         # Pydantic 请求/响应
├── corpus/

```

### 4.2 核心流程（RAG + tool use + 流式）

1. Java 门面 `POST /api/agent/chat` → 鉴权 → 建/载会话 → 持久化 user 消息 → 用 WebClient(SSE) 调 Python `/chat`，body：`{user_id, conversation_id, message, history}`。
2. Python `/chat`：
   - `embed(message)` → 从 corpus 检索 Top-K（如 5）相似片段（规则/FAQ/本地番剧）。
   - 组装 messages：`system`(角色定义 + 安全边界 + 检索上下文 + 来源署名要求) + `history` + `user`。
   - 调 LLM（`stream=true`，**带 `tools`**：3 个 Bangumi 只读函数）。
   - **若 LLM 返回 `tool_calls`**：执行对应 Bangumi 工具（命中 TTL 缓存）→ 把工具结果回填 messages → 再次调 LLM 生成最终回答（stream）。
   - 逐 token 以 SSE `data:{json}` 推回 Java → Nuxt。
3. 流结束：Java 累加完整回答 → 持久化 assistant 消息 → 首轮用前 20 字更新 `conversation.title`。
4. 异常（LLM 错误 / Bangumi 超时 / 限流）：推送 `event:error` 并落库；Bangumi 失败不影响基础 RAG 问答（回退）。

### 4.3 Bangumi 工具（关键，支撑番剧推荐）

复用 Java 端 `BangumiApiClient` 同款端点与 User-Agent（**只读 GET，无需 API key**）：

| 工具                       | 端点                                                  | 返回（取前 5）                          |
| ------------------------ | --------------------------------------------------- | --------------------------------- |
| `search_bangumi(keyword)` | `GET {base}/search/subject/{kw}?type=2&responseGroup=large` | name / name_cn / summary / rating / url |
| `get_bangumi_detail(id)`  | `GET {base}/v0/subjects/{id}`                       | 详情 / 标签 / 评分 / 集数                   |
| `get_airing_now()`        | `GET {base}/calendar`                               | 本周放送列表                            |

- `base-url` / `user-agent` 与 Java 端 `bangumi.api.*` 配置保持一致（从 `.env` 注入），不重复造配置。
- 内存 TTL 缓存（如 1h）尊重 rate limit；工具失败 → 返回提示，LLM 回退到 RAG 或礼貌说明。
- LLM 通过 function calling **自主决定**：用户问"类似 XX 的番""这季新番""机战番推荐"时触发对应工具。

### 4.4 语料与索引

- **rules/**：按小节切 300~500 字/段（抽赏保底、碎片合成、UR 兑换、积分、物流核销）。
- **faq.md**：一问一答一段（"怎么提现积分""订单多久发货""客服入口"）。
- **anime.json**：每番一部，含 `title/type/summary/rating`，用于"平台有哪些番"类问答与向量近邻"类似推荐"兜底。
- 构建：启动时加载 corpus → embed → 存内存列表（或 Chroma 持久化）。规则/番剧更新时重跑 `scripts/export_anime.py` + 触发 `/rebuild`（或重启服务）。
- **未来数据扩充**：BizAnime 增长 → 重导出 `anime.json` 自动纳入；推荐广度永远由 Bangumi 兜底。

### 5.2 流程与约束

- `POST /api/agent/chat`：鉴权（`SecurityUtils.getUserId()`）→ 建/载会话 → 持久化 user 消息 → `WebClient`(SSE) 调 Python `/chat` → 逐块转发 `SseEmitter` → 结束持久化 assistant 消息 + 更新标题。
- 复用 `@RateLimiterAndCircuitBreaker` 防刷与对 Python 服务熔断。
- 入参 `@Validated`（message 非空、长度上限）。
- **不**进 `permitAll`；所有请求必须登录。
- 系统边界兜底：即便 Python 返回异常，门面也保证会话记录完整（错误标记）。

### 5.3 数据模型（agent 自有，2 张表，遵循 BaseEntity 审计字段约定）

> 索引（向量/切片）由 Python 侧内存或 Chroma 持有，**不再落 MySQL 的 `agent_knowledge` 表**（见 §10 风险）。

```sql
-- 会话表
CREATE TABLE agent_conversation (
  id BIGINT PRIMARY KEY,
  user_id BIGINT NOT NULL,
  title VARCHAR(100),
  create_by VARCHAR(64), create_time DATETIME, update_by VARCHAR(64), update_time DATETIME, remark VARCHAR(500), del_flag CHAR(1) DEFAULT '0',
  INDEX idx_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 消息表
CREATE TABLE agent_message (
  id BIGINT PRIMARY KEY,
  conversation_id BIGINT NOT NULL,
  role VARCHAR(20) NOT NULL,        -- user / assistant / system
  content LONGTEXT NOT NULL,
  tokens INT,
  create_by VARCHAR(64), create_time DATETIME, update_by VARCHAR(64), update_time DATETIME, remark VARCHAR(500), del_flag CHAR(1) DEFAULT '0',
  INDEX idx_conv (conversation_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> 遵循 point.md 第 11 条：审计字段在 Controller 显式 set（项目无全局 MetaObjectHandler）；雪花 ID 走字符串化。

### 6.2 流式消费（关键）

```ts
// useAgentApi.ts
export function streamChat(payload: AgentChatReq, onToken: (t: string) => void, onDone: () => void) {
  return fetch('/api/agent/chat', { method: 'POST', body: JSON.stringify(payload), headers: { 'Content-Type': 'application/json' } })
    .then(r => r.body!.getReader()).then(reader => {
      const dec = new TextDecoder(); let buf = ''
      const pump = (): Promise<void> => reader.read().then(({ value, done }) => {
        if (done) return onDone()
        buf += dec.decode(value, { stream: true })
        buf.split('\n\n').forEach(block => {
          const line = block.replace(/^data:/, '').trim(); if (line) onToken(JSON.parse(line).content)
        })
        return pump()
      })
      return pump()
    })
}
```

## 10. 风险与规避

| 风险               | 规避                                                            |
| ---------------- | ------------------------------------------------------------- |
| 模型幻觉答错规则         | 强约束 System Prompt + 仅基于检索片段作答 + 关键规则附原文来源                       |
| API Key 泄露       | 仅 `.env`/环境变量，严禁硬编码；Railway 用变量注入                             |
| 流式中断/超时          | SSE 心跳 + 全局超时 + 错误事件兜底                                         |
| 语料过期（规则变更）       | 规则文档变更时同步重切 + 调 `/rebuild`                                  |
| 向量库内存占用          | 语料仅数百段；升级路径 Chroma / pgvector                                 |
| 限流失控成本           | Resilience4j 限流 + 单用户并发会话上限                                     |
| **Bangumi rate limit** | 内存 TTL 缓存（1h）+ 失败回退 RAG + 礼貌说明；工具超时不影响基础问答                    |
| **Bangumi 网络依赖**    | 工具调用失败 → 自动回退到 RAG/规则问答，不阻断对话                              |
| **python-agent 可用性** | Java 侧 Resilience4j 熔断 + `event:error` 兜底；`/health` 探针            |
| 索引落库取舍           | v1 索引存 Python 内存/Chroma（不落 MySQL `agent_knowledge`），避免双写一致性问题；如需跨重启持久化用 Chroma 持久化或本地 SQLite |
